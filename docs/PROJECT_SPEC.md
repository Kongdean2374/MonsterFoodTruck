## 2. 產品邊界、技術選擇與畫面結構

### 2.1 最終成品應有的樣子

打開 App 看見完整的黃昏森林餐車首頁，能開始、選關、讀取上次遊玩、改設定、查看操作教學及結束本次遊玩。進入關卡後，魔物排隊點餐；玩家安排兩個備料槽、兩個爐位及兩個成品位置。關卡結束有結果、星數、原因及重試／下一關。六關通過後有簡短完成畫面，並可重玩挑戰三星。

**忙碌來自選擇，不來自重複點擊。** 不要求連點切菜、攪拌、翻面；工作站自動完成計時工序，玩家決定開始及流轉時機。

### 2.2 工程預設

- Swift＋SpriteKit 遊戲場景，SwiftUI 導航與設定；可使用 `SpriteView` 嵌入場景。[S3]

- 只做 iPhone 直式，不加入橫式布局、iPad 專用介面或跨平台抽象層。
- 不要求 Mac 在使用者手邊；macOS 建置與模擬器驗證由可用雲端環境／Actions 執行。
- 優先 Apple 系統框架，避免為簡單需求加入大型相依套件。必要相依須固定版本、確認來源並記錄。

- Product name：`MonsterFoodTruck`；顯示名稱：「魔物餐車」；Bundle ID 暫定 `cc.chaihome.monsterfoodtruck`。這是本地工程設定，不代表 Apple 已註冊成功；目前不登入 Apple 註冊。
- 正式交付採一致的版本號與遞增 build number。可以有內部 build，不把完整功能拆成多次對外版本交付。

## 3. 完整遊戲流程與所有主要頁面

### 3.1 啟動／首頁

本地讀檔與預載必要素材，不要求網路。讀檔失敗提供恢復處理，不能無限 loading。

首頁有完整主視覺、遊戲標題、輕量動態餐車與以下功能：

| 按鈕 | 精確行為 |
|---|---|
| 開始遊戲 | 無進行中存檔時，進入下一個未通關關卡的簡介；已全通關則前往選關。已有未完成局時，先讓玩家選繼續或開始新局，不默默覆蓋 |
| 繼續遊玩 | 僅有有效進行中存檔時顯示，進入暫停的原局，玩家確認後才恢復 |
| 關卡選擇 | 進入六關畫面，展示解鎖、最高星數、關卡資訊 |
| 設定 | 開啟完整設定，返回後保留首頁狀態 |
| 遊戲說明 | 圖解料理流程、三種魔物與警告；可重看教學 |
| 關於 | 本地版本／build、製作資訊、素材來源與必要聲明，不顯示私人資訊 |
| 結束遊玩 | 保存進度、停止本次互動，顯示可自行離開 App 的說明；詳見 3.7 |

不放不能點的裝飾按鈕、不放「即將推出」項目，不用看似可按卻沒功能的圖示湊完整感。

### 3.2 關卡選擇

用森林小徑或六張精緻關卡卡片呈現，不新增第二套大地圖系統。每關顯示名稱、已獲得 0～3 星、可玩／鎖定狀態。第一關預設解鎖；通過前一關解鎖下一關，普通與舒緩模式都可解鎖。

點已解鎖關卡 → 簡介顯示本關料理、魔物、訂單數、通關目標、這關的一個重點 → 點「開始營業」。簡介期間遊戲不計時。最後一關通過後不顯示不存在的第七關。

有進行中局卻選另一關時，提供「返回繼續」「放棄目前這局並開始」。放棄僅清除該局快照，保留已得星數及解鎖。

### 3.3 教學

第一關先用一筆真實訂單，帶過選單、備料、下鍋、起鍋、出餐；下一筆再示範香草配料。教學提示每次只指向一件事，以實際成功事件推進，不以畫面停留幾秒就視為學會。

首次出現熱食、長工序、短起鍋寬限、偷吃／餐蓋時給短提示。教學提示會暫停全部遊戲時間；玩家確認後才繼續。可略過與重看，但不把重看教學混入正式成績。

### 3.4 遊玩中與暫停

暫停選單包含「繼續」「設定」「重新開始本關」「保存並回首頁」「放棄本局」。重新開始／放棄要確認；保存回首頁不清除快照。開啟設定、系統中斷或 App 失去 active 狀態時也暫停。

恢復時先顯示場景靜態與「繼續營業」按鈕；確認後可有短暫視覺倒數，倒數期間仍不扣任何遊戲時間。

### 3.5 結算

只有所有預定訂單均已正式入場並變成已服務／已離開，且不存在未解決的有效訂單時才結算。提前已無法通關也不強制打斷，可選擇重試。

結算展示：通過／未通過、星數、成功訂單數、偏好達成數、失單數、料理過熟／被偷嚐次數，以及最多兩個基於事件紀錄的改善提示。不要顯示沒實際發生的診斷。

提供「再玩一次」「關卡選擇」「回首頁」；通過且有下一關時提供「下一關」。儲存完成後再宣告新星數；重複結算、返回或重新啟動不能重複加分或錯誤解鎖。

### 3.6 全關完成

第六關通過後播放短而可跳過的收店／魔物致意動畫，展示六關最高星數總和，明確告知「六關已完成，可返回挑戰三星」。不假裝還有未製作的大量內容。

### 3.7 「退出遊戲」在 iPhone 的處理

保留使用者要的結束入口，但標示為「結束遊玩」，不要呼叫 `exit(0)`、`abort`、私有 API 或故意製造 crash。Apple 的封存技術說明指出不應透過 `exit` 終止 iOS App；文件年代較早，需按當前平台行為驗證。[S1]

實際行為：保存 → 暫停遊戲及音效 → 顯示「進度已儲存。你可以使用 iPhone 的系統手勢或主畫面按鈕離開 App。」並提供「返回首頁」。不宣稱 App 已關閉，不留下沒有返回方式的黑畫面。保存失敗時明說失敗，不顯示成功文案。

### 3.8 設定完整清單

| 設定 | 行為與保存 |
|---|---|
| 音樂音量 | 0～100%，可試聽、即時生效、永久記住 |
| 音效音量 | 與音樂獨立，0～100% |
| 觸覺回饋 | 獨立開關，無支援裝置安全略過 |
| 一般／舒緩模式 | 開局時鎖定，局中只能設定下一局使用；避免中途改計時造成不同步 |
| 高對比資訊 | 計時／訂單／文字對比提高，不只換背景色 |
| 大字介面 | 支援可用字級與布局重排，至少查驗標準及放大兩種 |
| 減少動態效果 | 降低晃動、粒子與背景動畫；不移除必要狀態資訊 |
| 左手／右手單手配置 | 改變底部常用操作排列；遊戲邏輯與站位不變 |
| 重新查看教學 | 從說明入口重看，不破壞目前關卡 |
| 恢復預設設定 | 確認後只重置設定，不清除星數 |
| 清除遊戲進度 | 另行二次確認，說明將清除星數、解鎖與目前局；取消不能改資料 |

## 4. 料理操作、狀態與資源規則

### 4.1 固定資源

兩個備料槽、兩個相同功能爐位、兩個成品位置、一個共用餐蓋。每格最多一份料理。原料無限，不加入採購、洗碗、垃圾桶經濟或數量補充。

每筆訂單有唯一 ID，綁定一份料理。第一個成品版不做同菜交換客人、預先製作未入場訂單、合鍋或自動出餐，避免隱藏分配規則。

### 4.2 一份料理的觸控路徑

1. **選訂單：** 點魔物訂單或底部快捷卡。對應料理包顯示明確標記。
2. **開始備料：** 點對應食材包／「備料」。空槽自動採固定順序分配，備料自動進行。點其他菜包只提示不符合訂單，不扣資源、不誤做一道菜。
3. **下鍋：** 備妥後點該槽，或選中訂單後點底部「下鍋」，送往第一個空爐。若爐滿，保留原狀並說明。沒有自動排隊下鍋。
4. **起鍋裝盤：** 料理完成後點爐位／底部「裝盤」，移至第一個空成品位。成品位滿時，食物仍在爐上且安全寬限繼續計時。
5. **配料或修整：** 裝盤後選擇需要的配料，耗時自動執行；也可不加配料直接出餐。焦邊／被偷嚐的料理先整理才能送出。
6. **出餐：** 按明確的「出餐」命令，自動送到綁定客人。不用拖曳、不用再選顧客。

普通流程約五次主要點按，加入配料約六次；切換關注訂單的點按另計。追求的是少做無意義操作，不是硬湊點擊數。

兩爐功能相同，不要求每次額外選左／右。底部快捷命令與點工作站必須觸發同一邏輯，不能存在不同的成功條件。

### 4.3 明確狀態

- 訂單：預定 → 入場等待 → 已服務／耐心耗盡離開。
- 食物：未開始 → 備料中 → 已備妥 → 烹調中 → 可起鍋／過熟 → 已裝盤 → 配料中／整理中 → 可出餐 → 已送出。
- 餐蓋：可用 → 蓋住某份成品 → 取下或出餐後歸還。
- `isCovered`、`everScorched`、`everNibbled`、偏好期限及配料是獨立狀態，不用單一複雜 enum 偷塞所有組合。

只允許合法轉移。對重複點按、過期事件、不存在的訂單、已失效的食物，安全拒絕且不產生第二份料理。每次實際操作產生唯一命令／事件，動畫不負責扣分、解鎖或計時真相。

### 4.4 時間基準

全部玩法使用同一個可暫停的遊戲時間，不以系統時鐘差推算背景期間。邏輯時間與畫面動畫分離；掉幀時按事件到期順序處理，不能因一次延遲讓完成、焦掉、偷嚐在同一個畫面無預警發生。

同時到期的邊界採玩家友善且確定的順序：先處理在截止前已接收的合法操作，再處理該時刻到期事件；恰在截止點的合法出餐視為及時。對事件時間排序、長畫格及暫停恢復建立測試，不用單純截短所有 delta time 偷改遊戲速度。

### 4.5 錯誤、修整與釋放資源

| 狀況 | 必須發生的事 |
|---|---|
| 備料／爐／成品位置滿 | 不移動、不耗掉食材、不排隱藏隊列；指出哪裡滿 |
| 選錯訂單或點錯菜包 | 可重選，已執行工序不受影響 |
| 烹調完成後超過安全寬限 | 變成可見焦邊狀態，但不永久燒毀；仍可裝盤 |
| 焦邊或被偷嚐 | 成品位執行 3 秒「整理」，恢復可出餐；該份永久失去偏好加分資格，正常出餐仍算成功 |
| 同時有兩種缺陷 | 一次 3 秒整理處理當下缺陷，不能反覆疊懲罰；永久失去偏好資格仍保留 |
| 配料加錯 | 可選另一配料重新耗時 2 秒替換；配料最多一種，不累積層數 |
| 配料進行中急著送 | 可按「取消配料」回到未加料，再出餐；不可把未完成配料算完成 |
| 客人離開 | 立即清理這筆訂單綁定的備料／鍋／成品、歸還餐蓋，取消相關事件；不讓孤兒料理塞死餐車 |
| 客人離開時正被偷嚐／整理 | 取消工作與警告，相關資源只釋放一次，不重複扣分 |

一般流程不需要「丟棄料理」按鈕；沒有錯誤配方時，加入此按鈕只增加誤觸。重新開始或放棄本局另有確認。

### 4.6 餐蓋

點選已裝盤且未配料／整理中的料理，按「蓋上」；餐蓋只有一個。蓋著不能配料／整理，但可直接出餐。按「取下」立即歸還；出餐時邏輯上立即歸還，動畫不得阻擋下一次合法操作。

餐蓋不延長熱度、不重置偷吃的已累積暴露時間或剩餘預告時間。蓋上可停止該盤被偷嚐並暫停其偷吃進度；取下時從保存的進度繼續，不讓反覆開蓋成為免費重置技。

### 5.3 偷嚐的完整規則

1. 至少有一位已正式入場且尚未被服務的小鬼時，別人已裝盤、未蓋、非整理中、尚未被偷嚐過的成品可被盯上。配料中仍屬暴露狀態。
2. 目前調整候選（2026-10-20，Content v2）：累積暴露 3 秒後，才進入明顯 3 秒預告；預告結束且條件仍有效，才偷嚐。原始 7 秒起始假設及診斷保留於 git 歷史與 `docs/QA/BALANCE_V2`；舒緩預告仍為 5 秒，不縮短反應預告。
3. 全畫面最多一個偷嚐預告／動作在執行。多隻小鬼不疊出無法處理的同時攻擊；按候選成品裝盤時間與訂單 ID 固定排序決定目標。
4. 不偷自己的餐點。若目標也是另一隻小鬼的訂單，只能由非該訂單擁有者的小鬼執行。執行者必須仍在場。
5. 預告清楚標示是哪一盤，不能僅顯示小鬼表情讓玩家猜。給可見的爪子圖示與倒數；不要用只有 1 秒的突襲。
6. 送走目標餐點、蓋上該盤、或先服務正在伸手的小鬼，均可阻止該次偷嚐。服務執行者後取消當前預告，其他仍在場小鬼可以之後依固定規則重新選目標。
7. 餐蓋暫停該盤的暴露／預告進度，不清零。新執行者也不能讓同一盤反覆獲得完整免費預告。
8. 每份餐點整局最多被偷嚐一次，整理後免再次被偷；偷嚐之後保留 `everNibbled`，不能因修整消除評分紀錄。
9. 兩次成功偷嚐間至少留 8 秒全域冷卻，冷卻期間不開始下一次預告。冷卻、目標及剩餘預告均屬存檔內容。
10. 如果受影響餐點在配料中，取消該配料進度，呈現需整理的狀態，不能同時得到尚未完成的配料。

**必要設計查驗：** 原始 7＋3 秒已由 3bc6d37 的 72 筆工程診斷觀察到無預告／無餐蓋；目前 v2 的 3＋3 秒及新交錯仍須原生與實際畫面重測。Dot 要觀察正常策略是否真的遇到有趣的保護選擇，不可以只靠故意站著不動的錄影證明機制有用。可優先調整暴露起始時間與訂單交錯，保留至少 3 秒清楚預告；不要新增無預告懲罰、強制扣餐或偷偷縮短所有顧客耐心。任何調整更新本節數據與測試，不保留互相矛盾的舊描述。

### 5.4 耐心與無障礙模式

客人正式入場才開始扣耐心；入場前等待位置不計時。剩餘時間以條＋圖示＋必要秒數顯示，低耐心有表情與視覺提醒。到 0 秒而尚未合法出餐才離開。

舒緩模式在開局固定：耐心 ×1.5、爐上安全寬限 ×1.5、熱食期限 ×1.5、偷嚐最後預告改 5 秒；備料、烹調與配料時間不變。普通與舒緩都能獲得三星與解鎖，不羞辱玩家；最高紀錄可另保存兩模式，選關總星數顯示兩者較高值並可看模式標籤。

### 5.5 星數與通關

令總訂單 `N`、成功送出 `S`、達成偏好 `P`：

- `S < ceil(0.75 × N)`：未通過，0 星。
- `S >= ceil(0.75 × N)` 且未全部服務：通過，1 星。
- `S == N` 且 `P < ceil(0.70 × N)`：2 星。
- `S == N` 且 `P >= ceil(0.70 × N)`：3 星。

單筆偏好最多計 1 次。曾焦邊或曾被偷嚐的餐點，整理後可算 `S`，但不算 `P`。不另外加入金幣、消費、連擊倍率或第二套隱藏評分。最高星數只升不降。

## 7. 正式美術製作：Codex 必做，Dot 獨立驗收

### 7.1 風格鎖定

採**溫暖童話手繪、乾淨柔和外輪廓、少量紙感、2D 分層動畫**。Q 版角色約 2 頭身，眼嘴在小尺寸仍清楚；背景低對比，操作物件高辨識。

不採恐怖、寫實怪物、廉價立體塑膠感，也不混合像素、照片、扁平 icon 與不同筆觸。不得直接模仿特定現役作品角色或要求複製特定藝術家的辨識風格。

| 色彩角色 | 起始色值 | 用途 |
|---|---|---|
| 奶油底 | `#FFF3D6` | 面板、文字背景 |
| 深可可 | `#3B2B2A` | 主要文字、輪廓 |
| 苔葉綠 | `#657B51` | 森林、鹿與香草 |
| 暖橘 | `#E98A49` | 龍、火候、暖光 |
| 小鬼紫 | `#8061A3` | 小鬼、個性點綴 |
| 青藍 | `#467F86` | 中性提示及冷色對比 |
| 焦糖金 | `#D6A54A` | 脆餅、完成獎勵 |

色值是視覺起點，不代表已通過對比測試。資訊優先於裝飾，警告要有符號與文字，不只改顏色。

### 7.2 先確認工具，再開始正式資產製作

建庫後盤點當前環境可用的圖片生成／編修、圖片檢視、透明背景處理、向量／分層編輯、音訊製作及預覽工具。能使用已授權圖片工具就使用，並實際保存與檢查輸出；不能把提示詞當完成素材。

OpenAI 官方文件提供圖片生成與參考圖編修工作流，但工具可用性與額度取決於當前環境，不能因文件存在就聲稱本任務一定能呼叫。[S7] 不新增付費 API 憑證，不私自把大量生成改為另行計費方案。

無圖片工具時，仍可用認真設計的原創分層向量／繪圖流程完成，前提是達到相同視覺品質。可程式繪圖不代表可以交圓形角色與方塊食物。若實際能力無法達標，列出缺失、已嘗試方案和需要的能力，由 Dot 擋下美術完成判定；其他不受阻的工作繼續。

### 7.3 製作順序

1. 先做一張三魔物母版設定板、一張餐車場景、一組三道料理，確立輪廓、比例、視角、光源及線條。
2. 將這組資產放入真實遊戲畫面，於小尺寸預覽。Dot 檢查不是只有大圖好看、縮小後全糊成一團。
3. 確認同一套風格後，才做其餘表情、部件、狀態與動畫。所有變體基於正式母版，不每次重新自由生成。
4. 分層拆件、整理透明邊緣、統一原點與縮放、建立圖集與資產清單，再整合場景。
5. Dot 檢視實際遊戲截圖與動態影片；不通過就針對缺陷局部修正，不隨意整套換風格。

### 7.4 必備素材與狀態

| 類別 | 必備內容 | 驗收重點 |
|---|---|---|
| 主視覺／首頁 | 同一輛餐車、森林背景、正式標題排版、可讀按鈕 | 不以海報大圖烘焙所有 UI，按鈕要真實可互動 |
| 餐車 | 至少背景、車體、檯面、爐具、成品區、前景幾層 | 視角統一；不擋計時與手指操作 |
| 角色 | 三隻獨立完整母版與可動畫部件 | 耳、角、尾巴、眼色及比例在所有狀態一致 |
| 角色表情 | 每隻至少待機、期待、低耐心、滿意、離開／失望五種 | 可由臉部組合實現，不必五張完整重畫 |
| 角色動作 | 點餐、待機、收到餐、吃一口、離場；龍尾焰、鹿聞香、小鬼預告與偷嚐 | 不以整張圖縮放冒充所有動作 |
| 三道料理 | 原料包、備妥、烹調表現、成品、焦邊／缺損、修整後 | 料理與容器有穩定形狀，三菜縮小仍可辨認 |
| 配料／餐蓋 | 香草芽、星脆片、餐蓋與放置效果 | 配料疊在對的位置，不貼成漂浮圖標 |
| UI | 關卡卡、鎖定、星數、訂單圖、耐心／進度／熱度／警告圖示 | 正常、按下、停用、選取狀態一致 |
| 特效 | 蒸氣、泡泡、煎餅滋滋、完成亮點、火苗與小量出餐粒子 | 重要提示有辨識，裝飾不搶畫面 |
| App 圖示／啟動 | 可辨識餐車與魔物主題的正式 icon、本地 launch 視覺 | 非預設 Xcode icon，無未確認權利標誌 |

### 7.5 素材格式與動畫技術

- 一般角色／料理：真正含 Alpha 的 PNG 或合適圖集。透明棋盤格只是預覽，不得印在像素裡。
- 角色母版建議約 1024px 級，實際輸出依呈現尺寸採適當 2x／3x；不把所有素材都做成 4K。
- 在深、淺兩底檢查白邊、黑邊、剪裁、透明蒸氣與陰影。Alpha、色彩空間及 premultiplied alpha 需與渲染設定一致。
- 角色部件採固定 anchor、比例和遮擋順序；動畫優先部件與少量關鍵影格，不依賴不穩定的自由生成影格串。
- 動畫由遊戲狀態驅動。預告開始、偷嚐成功與完成料理的時間點必須一致；暫停、恢復、場景切換不跳回錯誤狀態。
- UI 文案與數字使用真實文字排版；生成圖片上的假中文字不能作正式文案。
- 字型優先系統字型，不擅自打包或散布受限制字型檔。
- 留下可維護的母版／分層來源及生成處理說明；先確認該來源可放公開倉庫。選中的小型來源可版本管理，大批廢稿不要全部推送。

### 7.6 素材清單與權利紀錄

建立 `docs/ASSET_MANIFEST.md`，每項記錄：資產 ID、實際檔案、用途、尺寸／透明格式、來源或生成方法、日期、參考母版、修改方式、授權／服務條款查核來源、是否允許本次公開散布、查驗者與狀態。

不能寫「AI 做的所以沒有版權問題」或「已獲完整法律保證」。不能抓搜尋圖片、其他遊戲截圖或未授權音檔進正式版本。缺少權利依據的項目不得進公開成品；必要時以原創素材替換。

### 7.7 Dot 的美術門檻

以下六項各評 0～4，**每項至少 3，總分至少 20／24**，且不能有重大缺陷。分數是本專案品質量表，不是客觀市場認證；每項附實際截圖／影片位置及理由。

1. 角色與場景風格一致。
2. 小尺寸料理、魔物、計時狀態可辨識。
3. 角色表情與動作有個性，不是靜態貼紙堆疊。
4. UI 有完成品品質、對齊清楚、可讀且可操作。
5. 透明邊緣、圖層、動畫原點與畫面安全區無明顯瑕疵。
6. 忙碌場面仍能看懂目標、警告與可用空間。

未檢視素材與實際運行畫面時，不得評為通過。0／1 分缺陷、占位素材、生成畸形、假文字、缺貼圖或關鍵警告不可讀，直接退回。

## 8. 音效、音樂與觸覺

提供至少一首可循環的原創或具清楚使用依據的輕柔配樂；忙碌可用簡單節奏層，但不得讓背景音樂蓋掉警告。準備短結算提示，勝敗都不刺耳。不要使用辨識度高的現成歌曲或仿唱片段。

必備事件音：選取、備料開始／完成、下鍋、烹調完成、過熟預警、裝盤、配料、餐蓋、偷嚐預告／成功、出餐、達成偏好、顧客離開、通關／失敗。可共享素材變化，但備料完成、烹調完成與偷嚐預告必須可分辨。

至少三種角色有不同的非語言短反應；不要新增完整配音製作。沒有音樂生成工具時可製作原創簡單旋律與音色，但仍需聽取／分析實際輸出，避免音量失衡、循環接縫、突波與難聽的長蜂鳴。

以獨立音量控制、同時發聲數限制、短時間事件合併避免噪音。尊重系統音訊中斷與靜音行為，不使用背景音訊權限維持遊戲音樂；重回 App 不自動開始遊玩。觸覺輕且節制，備有關閉選項。

音訊權利與來源放入資產清單。音訊未實際聽過就標示「聽覺未驗證」，不能從檔案存在推論音質已通過；有可用播放／監聽工具的 Dot 必須執行。

## 9. 本機存檔、暫停、離線與無障礙

### 9.1 必須保存的內容

永久進度：資料格式版本、六關解鎖、各模式最高星數、教學完成旗標、設定。

進行中快照：關卡 ID 與資料版本、模式、遊戲時間、預定訂單游標／入場佇列、所有訂單與耐心、料理與工作站佔用、配料／整理進度、首次完成烹調時刻、缺陷紀錄、偷嚐進度／執行者／目標／冷卻、餐蓋歸屬、評分計數及必要事件摘要。

不要序列化整個 SpriteKit 場景樹或畫面動畫；從可驗證的邏輯快照重新建立視覺。儲存的穩定 ID 不依賴目前陣列位置。

### 9.2 寫入與恢復

- 重要操作、結算、手動暫停、離開 active 狀態時建立快照；遊玩中補充適度節流的週期快照，不每畫格寫磁碟。
- 使用序列化寫入與原子替換，保留一份最後有效備份。較舊的非同步寫入不能覆蓋較新狀態。
- 不只依賴 App 終止回呼存檔；不能保證終止前最後瞬間一定執行。異常終止允許恢復最近有效快照，必須明確標示實測可恢復範圍。
- 快照讀取時驗證版本、ID、數值範圍與資源不變量。壞檔先試備份；仍無法恢復時清楚提示，不當機、不把錯誤狀態當正常讀入。
- 關卡資料不相容時，保留永久進度，說明該進行中局需要重開。不可靜默刪除全部星數。
- 結算寫入與清除 session 要保持一致性；不出現已得星數又回到未結算局的重複獎勵。
- 更改手機日期、鎖定或長時間背景，不會讓料理、耐心、熱度或偷嚐繼續跑。

### 9.3 真正的離線

所有必要素材、關卡、音樂及說明隨 App 提供。飛航模式下可首次啟動、玩完六關、重啟恢復及改設定。不藏遠端圖庫、字型下載、登入 SDK、廣告／追蹤、生成服務呼叫或遠端關卡依賴。

遊戲不要求相機、麥克風、相簿、定位、藍牙、健康或通訊錄權限。素材生成只發生在開發環境，不是玩家遊玩期間。隱私清單與 API 聲明依實際使用項目核對，不把「離線」誤寫成不必檢查任何平台要求。

### 9.4 可及性要求

- 顏色以外還有形狀、圖示、文字／數字；高對比模式仍保有美術風格。
- 大字時重排，不能把耐心、出餐或返回按鈕裁掉。
- 左右手布局使用同一套玩法資料；底部可以完成選單、下鍋、裝盤、加料及出餐，無須反覆伸到頂部。
- 避免快速閃光、強烈畫面震動；跟隨系統「減少動態效果」或使用者開關。
- 菜單與主要控制有明確無障礙名稱／狀態，包含菜名、客人、剩餘時間與可操作動作。SpriteKit 圖形必要時提供對應 accessibility elements，不把整張畫布當無名稱圖片。
- VoiceOver 不逐畫格播報時間。基本導航與關鍵動作須測試；完全非視覺通關能力若未驗證，明確記錄，不宣稱全面支援。
- 舒緩模式延長反應時間，不移除核心選擇，也不扣減可獲星數。

### 10.1 建議目錄

### 10.2 核心工程要求

1. 建立不依賴 SpriteKit 渲染的邏輯模型，透過命令／事件處理訂單、工序、評分與計時，UI 不直接任意修改分數。
2. 關卡資料可新增而不改寫核心流程。載入時檢查不存在的魔物／食譜、負數時間、重複 ID、錯誤門檻與素材缺失，錯誤要可理解。
3. 使用單一受控狀態寫入路徑。音效與動畫消費事件，不以動畫完成回呼決定料理「真正完成」。
4. 暫停、取消、重試、返回首頁要清理舊 session 的事件與訂閱。舊任務不能回來改新局。
5. 不用強制解包、忽略所有錯誤或大量 `try?` 掩蓋失敗；可以安全降級的狀況要明確設計。
6. 生成／下載依賴、資料 schema、素材映射、工程設定與建置腳本皆可重現，必要版本固定。
7. 不引入伺服器、線上資料庫、通用外掛引擎或跨平台框架來「預留未來」。
8. 僅 Debug 提供測試入口，例如載入固定局面、顯示診斷數值；使用者產物不得有解鎖全部關卡、無限耐心或自動出餐捷徑。

### 10.3 效能目標與測量

以 iPhone 17 Pro 為使用者最終試玩目標，但未取得裝置實測時不能寫成已驗證。

設計目標：遊玩 60fps；常態點按視覺回饋盡量在 100ms 內；不在觸控主路徑解碼大圖、生成音訊或同步寫大量資料。場景重進 20 次不應出現持續增加的角色節點、事件訂閱或音效實例。

首輪可先把高峰記憶體 250MB、IPA 150MB 內作診斷預算，不是 Apple 限制或使用者硬性容量需求。超出時解釋主要資源與優化，不能為追數字破壞畫質；模擬器與真機數據分開。

需要真實記錄測量方式、裝置／模擬器、OS、build、冷／熱啟動、測試場景及觀察。沒有測到就標示未測，不用估算冒充 60fps 實證。

## 11. GitHub Actions、未簽名 IPA 與公開建置安全

### 11.1 現階段只做兩條工作流程

| Workflow | 觸發 | 工作 | 不得做 |
|---|---|---|---|
| `validate.yml` | PR、程式／素材變更的 push、手動 | 資料／資產檢查、單元測試、可用模擬器 UI 測試與證據 | 不取 Apple secrets、不簽正式 App、不送審 |
| `unsigned-ipa.yml` | `workflow_dispatch` 手動，預設可信 `main` | 驗證同一提交、Release 裝置建置、封裝、檢查、上傳產物 | 不把外部 PR 直接當可信發布來源、不自動發商店 |

先在已確認可用的標準 GitHub-hosted macOS runner 上做。公開倉庫的標準 runner 執行分鐘目前免費，但大型 runner 仍收費，artifact／cache 儲存也須依實際帳號與規則確認；不可承諾任何用量都免費。[S4]

明確固定可用 runner 標籤與 Xcode 選擇，記錄 runner image、Xcode、SDK、Swift 與模擬器 runtime 版本。不靠未說明的 `latest` 漂移維持建置；必要更新先驗證。

### 11.2 未簽名建置與封裝要求

- 從確切完整 Git commit SHA 建置，工作目錄須無未提交的程式／資產變更。
- 用真實 iPhone 裝置 SDK，Release configuration，generic iOS destination。模擬器 `.app` 不能改壓縮副檔名冒充可供真機簽署的 IPA。
- 使用確實可用的無簽名 archive／build 流程，例如驗證 `CODE_SIGNING_ALLOWED=NO`、`CODE_SIGNING_REQUIRED=NO`、空 `CODE_SIGN_IDENTITY`／`DEVELOPMENT_TEAM` 等設定。這些是需實測的建置方向，不代表範例旗標本身已完成驗證。
- 若 `-exportArchive` 要求 provisioning，不能靠偷放憑證過關。可從成功裝置 archive 的應用程式輸出取得 `.app`，以 `Payload/MonsterFoodTruck.app` 正確結構封裝成 ZIP 格式 IPA。
- 不手動刪除建置必需的 Swift runtime、改造可執行檔或套用簽名繞過。採系統框架優先，減少額外 embedded framework 的封裝風險。
- 檢查 Mach-O 不只是 arm64，還需確認平台是 iOS device 而非 iOS simulator；Apple silicon 模擬器同樣可能是 arm64。
- 檢查 Info.plist、Bundle ID、版本、部署目標、可執行檔、必備素材、音訊與所有六關均存在；無錯誤的巢狀 Payload、空殼 App 或缺失貼圖。
- 檢查未夾帶實際 provisioning、開發者私鑰、token、使用者資料與不必要的 build 快取。回報簽名狀態，不能把 ad hoc 簽名與可安裝的 Apple 簽名混稱。
- 使用者收到的是未簽名 IPA，仍需自行簽名後才能在一般 iPhone 安裝；不能寫「直接點擊安裝」或「已通過 Apple 審核」。[S8]

### 11.3 可追溯產物

成功產物至少包含：

| 檔案 | 內容 |
|---|---|
| `MonsterFoodTruck-unsigned-<version>-<build>.ipa` | 實際未簽名裝置包 |
| `SHA256SUMS.txt` | IPA 與必要交付檔案的 SHA-256 |
| `BUILD_MANIFEST.json` | 完整 source SHA、版本、build、runner、Xcode／SDK、Bundle ID、產出時間、workflow run ID、IPA checksum |
| `TEST_SUMMARY.md` | 實際執行／成功／失敗／略過測試，證據位置 |
| `QA_EVIDENCE/` | 乾淨的實際 App 截圖與短影片，標示 build／裝置／模式 |
| `PLAYTEST_GUIDE.md` | 內容、操作、未簽名說明、已知限制及真機待驗證項 |

Artifact 名稱含 build 與短 SHA；manifest 保存完整 SHA。不得用過期的另一筆成功紀錄包裝目前提交。

保留期限先採合理短期，例如 14 天，顯示實際到期／取得方式；只上傳必要產物，不把 DerivedData 全部當交付。下載可能要求 GitHub 登入，README 應說明。IPA 不提交進 git 歷史；目前也不自動建立公開 GitHub Release。

### 11.4 CI 安全規則

- 預設 `permissions: contents: read`，只在確有必要的特定 job 提升權限；不得為方便改成 write-all。
- 使用 `pull_request` 的低權限檢查；本案不需要 `pull_request_target` 或會執行不可信內容的特權接力。
- 第三方 Actions／建置依賴鎖定到可信版本。現行文件若支援且適用 workflow dependency lockfile，可採用；否則至少固定驗證過的完整 commit SHA，不只用可移動標籤。[S5]
- checkout 預設不保留後續 Git 認證；不直接把 PR 標題、分支名或使用者輸入插入 shell 執行字串。
- 使用 concurrency 避免同分支冗餘執行、設定合理 timeout，不用無限 retry、排程輪詢或大型矩陣浪費額度。
- 避免讓外部 PR 汙染可信產物快取；快取不包含秘密，不上傳整個 home 目錄。
- 原始碼、日志、截圖與 manifest 都做公開內容檢查；敏感值沒有出現在 Secrets 不代表可以明文公開。
- 現階段不設 Apple secrets、不建立正式上傳工作，不使用使用者其他 App 的憑證。

### 11.5 未來發布只留文件邊界

可在 `BUILD_GUIDE.md` 記錄：未來 TestFlight／App Store 另行授權、簽名與上傳分離、受保護環境、可信提交及人工核准。不要現在實作一個只差填入密鑰就會自動送審的工作流程。

## 12. 測試計畫與必備證據

所有測試須區分「實際跑過」「靜態檢查」「人工檢視」「未驗證」。單純新增測試檔不等於測試通過；模擬器錄影不等於真機性能。

### 12.1 邏輯與資料測試

至少涵蓋下列情境，允許多個情境合併為參數化測試，但不得用一個永遠回傳成功的 stub 充數：

| 類別 | 必測情境 |
|---|---|
| 資源不變量 | 兩備料／兩爐／兩成品不超量；同份料理不能出現在兩站；全局最多一餐蓋 |
| 命令合法性 | 重複點按、點忙碌／已滿站、已離開訂單、過期事件都不複製料理或扣錯分 |
| 時間 | 同時完成、截止前／恰在截止／超時；掉幀；長時間背景；多次暫停恢復 |
| 食譜 | 三菜所有合法路徑、備料時間、烹調、寬限與焦邊一致 |
| 熱度 | 自烹調完成算；鍋上、蓋上、配料不重置；暫停不流逝 |
| 小鬼 | 無小鬼不偷；不偷自己；目標明確；餐蓋／出餐／送走執行者可阻止；最多一預告；每盤最多一次 |
| 修整 | 焦邊／偷嚐後可恢復出餐；不恢復偏好分；整理取消／客人離開安全 |
| 配料 | 正確、錯誤替換、取消、過程被偷、已蓋餐點禁止配料 |
| 訂單 | 入場佇列、最多三客、四秒預告／間隔、耐心起算、失單清理、不孤兒化 |
| 評分 | 六關各門檻、向上取整、重複出餐與結算、最高星數只升不降 |
| 存檔 | 各工序 round-trip、壞檔／備份、版本不相容、同時寫入順序、結算一致性 |
| 關卡 | 六關資料驗證、參考操作重播、普通／舒緩規則差異、沒有非法資源使用 |

時間與策略測試使用實際 Domain 模型，不另用一份與遊戲不同的簡化計算器宣稱關卡可解。重播輸入須經與 UI 相同的命令驗證，不能直接把分數或料理狀態改成成功。

### 12.2 UI／流程回歸

1. 乾淨首次啟動 → 首頁 → 開始 → 教學 → 第一關結算 → 解鎖第二關。
2. 選關 → 六關逐一實際遊玩或由正常命令重播 → 結算 → 最後通關畫面。
3. 失敗 → 查看原因 → 同關重試，訂單腳本不改。
4. 三種料理同時出現、兩鍋完成接近、成品台滿、焦邊、低耐心及偷嚐警告。
5. 正常開蓋／取下／出餐及錯誤操作，沒有小按鈕或跨層誤觸。
6. 暫停 → 設定 → 回遊戲；保存回首頁 → 繼續；放棄／重開的取消與確認。
7. 系統背景／鎖定或對應模擬器中斷 → 恢復，所有倒數不偷偷流逝。
8. 進行中快照存妥後終止 App → 重開 → 正確恢復；結算後重開不重複獎勵。
9. 音樂／音效／觸覺開關、高對比、大字、左右手、減少動態及舒緩模式。
10. 飛航／斷網啟動及完整遊玩，沒有必要網路請求。
11. 清除設定與清除進度分離；各取消路徑不刪資料。
12. 首頁結束遊玩顯示保存結果，沒有強制終止或假關閉。

### 12.3 最低畫面證據包

每張圖要由實際運行的 App 擷取，而非生圖、Figma 設計稿或合成預覽。至少提供：

- 首頁、六關選擇（含鎖定與解鎖狀態）、關卡簡介。
- 教學第一步、一般遊玩、忙碌遊玩、三種魔物同場。
- 小鬼預告與目標、焦邊整理、餐蓋、熱度剩餘等清楚狀態。
- 暫停、設定、成功／失敗結算、六關完成。
- 小尺寸、大字、高對比、左手與右手的關鍵布局。

另錄至少一段完整一般玩法與一段第五／六關挑戰流程，含遊戲音訊者應可供監聽；無法取得音訊時明確記錄。Debug 注入情境的截圖可補充狀態覆蓋，但標示為測試情境，不能取代正常遊玩影片。

### 12.4 「好玩」的工程期檢查

Dot 至少比較三種安排：短菜優先、長菜預先下鍋、依耐心／熱度／空間動態調整。觀察是否出現不同結果與可解釋取捨，而非只有等待亮燈。

需要記錄：無操作等待段落、無效／多餘點按、警告是否來得及反應、配料是否有放棄價值、餐蓋是否有實際用途、失敗原因是否能從畫面理解。若明顯單調，調整節奏與呈現，不任意加大量新系統。

這些檢查不能冒充真人玩家試玩或市場驗證。使用者首次真機試玩仍是驗證手感的一部分；不以必須先找八位玩家為理由阻止完整試玩包交付。

## 13. 分階段開發，但只以完整成品作最終交付

每階段是內部工作關卡，不是「這版先沒有美術、下一版再做設定」的產品拆分。Codex 應在可用工作階段內持續推進，不每完成一個普通步驟就要求使用者同意。Dot 在有實際接手能力時依證據查驗；未取得 Dot 判定不能冒寫「Dot 已通過」。

| 階段 | Codex 必須完成 | Dot 查驗與通過條件 |
|---|---|---|
| P0 權限與倉庫 | 帳號／權限確認、建立或核對公開倉庫、再保存本規格與工作紀錄 | 倉庫擁有者、可見性、寫入範圍正確；沒把其他私人資料搬入 |
| P1 可建置工程與視覺定案 | 可啟動原生工程、最小裝置建置；三角色／三菜／餐車母版與實際布局樣本 | CI 真正跑過；正式美術方向一致、小畫面可讀；阻礙已具體揭露 |
| P2 核心規則完整 | 三食譜、三魔物、兩備料／兩爐／兩成品／餐蓋、計時與評分、模型測試 | 正常、錯誤、滿站、偷嚐、熱度、重複輸入及清理行為符合規格 |
| P3 全流程與六關 | 首頁、選關、教學、所有關卡、設定、存檔、恢復、結算、通關；整合全部正式素材音效 | 不存在未接線按鈕、缺關卡、占位畫面、無法返回或名義支援的設定 |
| P4 整合查驗與返工 | 真實 UI／模擬器測試、三種尺寸、效能診斷、素材修整、關卡調校 | Dot 提修正單，Codex 修正後附證據；已關閉問題需回歸而非只看回覆 |
| P5 最終候選與交付 | 乾淨提交、同 SHA 全檢查與裝置 IPA、校驗碼、證據及交付說明 | Dot 依第 17 節判定，交付的是被查驗內容，不是另一個較新／較舊 build |

Codex 可先完成不受阻的工作；例如等待獨立圖片檢視時可完成模型測試，但不能將未過視覺門檻的資產當正式定案後大批擴充。任何階段結束不代表可以刪掉其他必做內容。

### 13.1 對使用者的進度回報

每次重大里程碑、Dot 退件或阻礙時簡短回報，避免持續輸出大量流水帳。包含「目前階段／完成的證據／還缺什麼／下一步」。有工具錯誤立即標示；無法工作的時間不聲稱在背景繼續處理。

## 14. Dot 監工操作手冊

本節對 Dot 是直接工作指令，不依賴使用者再口述品質標準。

### 14.1 啟動監工時的固定動作

1. 讀 `docs/PROJECT_SPEC.md` 全文與根目錄 `AGENTS.md`，再讀 `WORK_STATUS.md`、決策紀錄及既有問題單；不可只讀簡短 README 就審核。
2. 透過實際 GitHub／檔案工具確認倉庫 URL、目標分支、完整提交 SHA、最近差異、Actions 狀態與產物。聊天內聲明不是證據。
3. 確認你當前能做哪些事：讀檔／看圖／看影片／聽音訊／操作模擬器／下載產物／聯絡 Codex。不能做的項目列為能力缺口，不假裝測過。
4. 確認 Codex 是否已有唯一活動任務。沿用該任務、分支及工作進度，不因訊息中斷另開一個並行開發者。
5. 對照目前階段檢查對應證據。早期沒有最終圖片可以標示尚未到階段，最終候選仍缺則必須退回。
6. 建立具體修正單，依嚴重度和依賴順序交回 Codex；修正後核對差異與重測。

### 14.2 不能只檢查「有沒有檔案」

- 有三張角色圖，不代表角色一致、透明正常或遊戲中可讀。
- 有 `SaveManager`，不代表背景／壞檔／重啟恢復可靠。
- 有六份 JSON，不代表六關可玩或三星可解。
- 有「設定」按鈕，不代表音效、字級與模式真的生效。
- 有 `.ipa`，不代表是裝置版本、目前提交或封裝正確。
- Actions 綠燈，不代表未被忽略的 UI 失敗、沒跑的測試或藝術品質通過。

Dot 必須追到實際輸出、實際 UI 行為與所測提交。

### 14.3 缺陷分級

| 等級 | 例子 | 處置 |
|---|---|---|
| P0 安全／資料災難 | 公開憑證、讀寫其他私人專案、破壞既有資料 | 停止相關危險操作、保全現況並立即回報；不可私自重寫歷史掩蓋 |
| P1 阻擋使用 | 無法建置／啟動／通關、存檔嚴重錯亂、IPA 平台錯誤、核心操作失效 | 不得交付為可試玩成品，優先修正與回歸 |
| P2 必做品質未達 | 缺正式美術、警告看不懂、缺關卡、設定空殼、明顯裁切／動畫變形、缺必要證據 | 必須返工；不能以「下次更新」規避本規格 |
| P3 非阻擋改善 | 不影響功能的小裝飾瑕疵、非必需視覺潤飾 | 可記錄，但不讓此類項目無限擴大本案 |

必做功能不能因趕交付而自行從 P2 降成 P3。無法測量不等於沒有問題，使用 `UNVERIFIED` 明確標示。

### 14.4 每張修正單的固定格式

```text
Issue ID：DOT-001
嚴重度：P0／P1／P2／P3
規格條款：例如 4.6 餐蓋、7.7 美術門檻
受測 source SHA／build：
環境：模擬器或真機，型號／尺寸、OS、模式
問題摘要：
重現步驟：
預期結果：
實際結果：
證據：實際檔案／Actions／影片時間點，非概念圖
要求修正範圍：
回歸項目：
Codex 修復提交：
Dot 重測證據與結果：
狀態：OPEN → IN_PROGRESS → READY_FOR_RETEST → VERIFIED_CLOSED
```

沒有重測證據，不得從 Codex 的「已修正」直接跳到關閉。重測失敗回到 OPEN，保留歷史，不刪掉失敗紀錄。

### 14.5 交回 Codex 的修正指令模板

```text
請沿用目前 MonsterFoodTruck 倉庫與同一開發任務，先核對 git 狀態與現有變更。
本輪處理：<Issue IDs 及規格條款>。
保留已完成且已驗收的功能與美術，不另開並行 writer，不 reset、不 force push。
依每張修正單重現 → 修正 → 加回歸測試 → 實際執行 → 更新證據。
回報完整提交 SHA、改動內容、測試結果與仍未驗證項。
不要上傳 TestFlight／App Store，不要求使用者補美術來替代本任務。
完成後標示 READY_FOR_RETEST，等待 Dot 獨立重測，不能自行標示 Dot 通過。
```

### 14.6 審核循環及中斷恢復

Codex 實作 → 自測 → 提交證據 → Dot 查驗 → 修正單 → Codex 修正 → Dot 重測 → 進入下一個品質關卡。不要讓使用者逐條充當中間人；有實際聯絡權限時，由兩者在同一任務／授權管道交換資料。

若沒有跨代理聯絡能力，只能產出待執行修正單，說明需要哪個管道；不能用文字假裝另一個代理人已接到工作。真正持續監看需要目前環境支援的任務／事件或排程能力，沒有就回報目前一次檢查的結果，不宣稱已設定自動監控。

訊息中斷後先核對 git status、最後成功提交、未提交修改、活動任務與最新問題狀態，再續作。不能丟掉已做內容重新生成。相同錯誤連續兩次無有效改變時，先診斷原因或換可驗證方法，不無限重試消耗資源。

## 15. 協作檔案、單一寫入者與證據追溯

### 15.1 工作狀態

`docs/WORK_STATUS.md` 至少保留：目標倉庫／分支、目前階段、最近交付審核的 source SHA、活動任務識別（確有其物才填）、目前產品檔案寫入者、已完成項目、未完成項目、阻礙、未結問題 ID、下一個實際動作。

這份狀態檔是交接紀錄，不是能自行防止並行寫入的鎖。Codex 對程式／素材保持單一寫入者；Dot 在自己的審核目錄／分支記錄，不同時覆寫 Codex 工作樹。合併審核文件也要經既有協作流程。

不要求在某提交內寫入「本提交自己的 SHA」這種無法穩定自指的值。被審核 SHA 記錄於後續審核報告或 CI 產物即可。

### 15.2 建議證據索引

每次候選附一個簡單證據索引，記錄：

- `reviewed_source_sha`：實際 App 原始碼／素材／設定的完整 SHA。
- `workflow_run_id`、`artifact_name`、`ipa_sha256`。
- `test_environment`、`executed_tests`、`skipped_or_unverified`。
- `screenshots`、`videos` 與音訊檢視狀態。
- `open_issues`、`dot_verdict`、`reviewed_at`、`reviewer`。

審核報告可以作 artifact 或單獨審核文件提交。報告提交與 App build SHA 不必相同，但一定要分清楚。任何影響遊戲、素材、設定或打包的修改，必須重新建置並重測受影響項；不能拿舊 IPA 配新報告。

### 15.3 文檔最低內容

- README：遊戲內容、操作、正式截圖、如何從 Actions 找到 IPA、未簽名提醒、目前驗證狀態。
- BUILD_GUIDE：乾淨環境建置流程、實際工具版本、產物位置及失敗排查，不要求私人路徑。
- ART_DIRECTION／ASSET_MANIFEST：母版規格、完整來源與透明／動畫檢查。
- TEST_PLAN／ISSUE_LOG：真實測試矩陣、證據與問題生命週期。
- DECISIONS：玩法數值調整、操作簡化及重要工程選擇的理由，不記錄私密聊天。
- PLAYTEST_GUIDE：給使用者的簡短操作、已知限制、真機驗證清單。

文件應服務交接與再現，不為湊數建立大量空檔。每個文件的「通過」都要對應證據。

## 16. 阻礙與權限不足的處理

| 阻礙 | 正確處理 | 不得做 |
|---|---|---|
| 無法建庫 | 回報實際缺的權限與精確倉庫名稱，等待建庫後再寫專案 | 先寫一大包，或寫進其他專案 |
| 無法生成／編修正式美術 | 嘗試可達同品質的原創工具流程，列能力缺口；繼續不受阻工作 | 把 emoji／幾何占位圖標成正式完成，或虛稱素材存在 |
| 素材額度／費用不足 | 保存已有成果與所需項目，說明阻礙 | 擅自另開收費 API、購買素材或續費 |
| 沒本地 Mac | 使用已授權 macOS CI／雲端能力實際建置 | 把「Swift 語法看起來正確」當 iOS 編譯成功 |
| 缺模擬器／視覺證據 | 排除 CI 環境問題或尋找已授權可用環境；標明尚未驗證 | 用設計稿／生圖偽造 App 截圖，宣稱完整驗收 |
| Dot 無法操作或聯絡 Codex | 交付可執行修正單，標示待聯絡，不誤稱已開始監控 | 建立假的任務 ID 或替對方宣告完成 |
| 使用者真機尚未試玩 | 在模擬器及封裝通過後標為「可交付試玩，真機待驗證」 | 把未親測裝置列為通過，或因此永遠不提供試玩包 |
| CI 權限／服務中斷 | 回報是哪筆執行失敗、已嘗試什麼與下一步；保留現有成果 | 建置失敗仍複製舊 IPA 冒充新版本 |

重要原則：不受阻工作繼續；阻礙與缺陷不被隱藏。使用者要求一次完整交付，不等於可以省略真實限制或繞過權限。
